# 구현 진행 로그

`docs/architecture.md`의 로드맵(§10) 대비 실제 구현 상태를 기록한다. 설계 자체가 바뀌면 architecture.md를, 무엇을 언제 어떻게 만들었는지는 이 문서를 갱신한다.

### 28단계 — 전체 코드베이스 리뷰로 데이터 손실/유실 위험 3건 수정 (2026-07-31)

27단계 직후 사용자 요청으로 퀴즈 이외 전체 모듈(하드웨어/비전/디스플레이/미디어/launcher.py)까지 서브에이전트로 훑어보고, 발견된 항목을 직접 코드로 재검증한 뒤 우선순위가 높은 3건을 수정.

1. **`core/profile_manager.py` — JSON 손상 시 전체 참가자 데이터가 조용히 날아갈 수 있던 위험.** `_load_all()`이 파싱 실패 시 경고 없이 `{}`를 반환했었는데, 그 직후 `remember_fact()`가 호출되면 "원래 비어있던 저장소"로 착각해 지금까지 쌓인 모든 참가자 프로필을 통째로 덮어쓸 수 있었다(N=30 연구 데이터가 파일 하나에 누적됨 — 메모리에 남아있는 2026-07-28 테스트 데이터 실수와 결이 같은 위험). `_save_all()`도 임시파일 없이 직접 덮어써서, 쓰기 도중 프로세스가 죽으면(Ctrl+C, 크래시, 정전) 파일이 손상된 채 남을 수 있었다. **수정**: `_save_all()`을 임시 파일 + `os.replace()`로 원자적 쓰기로 전환, `_load_all()`은 파싱 실패 시 손상된 원본을 `.corrupted-{타임스탬프}`로 백업해두고 크게 경고하도록 변경. 임시 파일로 원자적 쓰기/손상 복구 시나리오 모두 검증(실제 `user_profiles.json`은 건드리지 않음).
2. **`launcher.py` — 툴 호출 중 예외 하나가 세션 전체를 크래시시켜 대화록·결과지·퀴즈 데이터가 통째로 유실될 수 있던 위험.** `recv_loop`의 툴 디스패치(`fn(**(fc.args or {}))`)에 예외 처리가 없어서, 아무 툴에서든 예외가 나면 `asyncio.gather`를 통해 전파되어 `run_conversation()`이 비정상 종료되고 `session_history`/`quiz_log_out.extend(...)`가 실행되지 못했다(물리적 안전 정리는 `finally`가 그대로 실행하므로 모터 쪽은 안전했지만, 연구/대화 데이터가 유실됨). **수정**: 툴 디스패치를 try/except로 감싸 개별 툴 실패를 그 자리에서 흡수(`"tool call failed: ..."`를 모델에게 반환)하고 세션은 계속 진행되게 함.
3. **`core/report_manager.py` — 대화록/결과지 파일명이 날짜+이름뿐이라 같은 날 재실험 시 덮어쓰기 위험.** `core/quiz_export.py`는 22단계에서 이미 같은 문제를 겪고 시각(HHMMSS)까지 파일명에 넣어 고쳤는데, report_manager.py에는 그 수정이 반영 안 돼 있었다. **수정**: 같은 방식으로 시각을 파일명에 추가.

나머지(낮은 우선순위로 분류): `vision/face.py`의 추적 루프가 예외 시 스레드가 조용히 죽고 재시작 안 됨, `hardware/motion.py`의 `_dance_routine`도 같은 try/finally-no-except 패턴, 종료 시 `t_face.join(timeout=5.0)` 타임아웃과 포트 종료 사이의 미세한 레이스, 바지인 직후 VoiceShifter의 미세한 오디오 잔여 경합 — 전부 크래시가 아니라 해당 기능만 조용히 죽는 수준이라 우선순위를 낮게 매기고 이번엔 보류.

**검증**: `python -m py_compile`로 세 파일 전부 통과, 기존 오프라인 테스트(`test_quiz_state`/`test_quiz_tools`/`test_quiz_bank`/`test_emotion_tools`/`test_memory` 1부) 전부 재통과. profile_manager.py의 원자적 쓰기/손상 복구는 임시 디렉터리로 직접 시나리오를 재현해 검증(정상 저장 후 `.tmp` 파일이 안 남는지, 고의로 손상시킨 파일이 백업되고 빈 저장소로 시작하는지, 그 이후 저장이 정상 동작하는지). **launcher.py의 툴 예외 흡수는 실제 Live API 세션으로는 아직 확인 안 됨** — 다음 로봇 연결 때 의도적으로 잘못된 툴 인자를 유발해보거나, 다음 예외가 실제로 났을 때 세션이 계속되는지 관찰 필요.

### 27단계 — 짜증유발 모드 3차 재설계: 항상 거절, 명시적 포기 시에만 정답 공개 (2026-07-31)

26단계 직후 사용자에게 "전체 로직이 실험 조건과 잘 부합하는지" 평가를 요청받아 코드를 조작 점검 문항과 대조 검토하다가, 26단계의 "거절 대사 한 번 → 곧장 정답 공개" 설계 자체가 새로운 서사 모순을 만든다는 걸 발견해 보고함: 참가자 입장에서 "AI라서 답 못한다"고 거절해놓고 몇 초 뒤 바로 정답을 술술 말해버리면 "사실 알고 있었으면서 안 알려준 것"으로 읽혀, "시스템 한계로 대답 못한다"는 조작 점검 문항의 타당도를 해칠 수 있다는 지적. 사용자가 대안을 직접 제시: **사용자가 무엇을 답하든(오답이든 정답이든) 매번 거절만 하고, 참가자가 답답해서 명시적으로 "정답 공개해줘"/"다음 문제로 넘어가줘"라고 포기·스킵을 요청할 때만 그때 정답을 공개하고 다음으로 넘어간다.** 이때도 "제가 아는 게 아니라 화면에 적힌 걸 읽어드리는 것"이라는 서사를 유지해 모순을 최소화.

**구현**: `core/quiz_bank.py`의 `_DONT_KNOW_MARKERS`에 "넘어가"/"스킵"/"공개해"/"그만" 추가 — 이 표현들이 짜증유발 모드의 포기·스킵 신호로 쓰인다(다른 모드에도 같은 마커가 적용되지만 의미상 무해함: all_knowing은 애초에 dont_know 분기가 오답과 동일하게 처리되고, imperfect는 "넘어가줘" 같은 표현이 실제 답이 아니므로 기존 포기 이벤트로 가는 게 오히려 맞음). `core/quiz_state.py`의 `resolve_user_guess` annoying 분기를 재작성 — `is_dont_know`면 뜸들이지 않고 그 자리에서 곧장 `_record_and_advance` + "화면에 적힌 정답은 X" 서사로 응답, 아니면(실제 답 시도, 정오 무관) 침묵 지시만 반환하고 아무것도 기록/전진하지 않는다. 직전 실제 답 시도가 있었다면 그 정오(`annoying_pending_correct`)를 포기 시점 로그에 보존한다(조작 점검/정답률 지표용). **`confirm_annoying_correct()`/`reveal_annoying_wrong()` 메서드와 `CORRECT_STALL_MIN/MAX_SEC`, `_pending_stall`의 kind 추적을 전부 제거** — 정답/오답을 다르게 취급할 필요가 없어져 24~26단계보다 코드가 오히려 단순해짐. `core/quiz_tools.py`의 `_delayed_refusal()`은 거절 대사만 말하고 멈추도록 되돌리고, `submit_guess()` 래퍼는 `resolve_user_guess` 호출 후 `session.results`가 늘었는지(포기 경로로 즉시 해결됐는지)만으로 "남은 거절 스톨 취소" vs "새 거절 스톨 예약"을 가른다. `core/utils.py`의 퀴즈 지시 블록도 갱신 — 짜증유발 모드에서 포기·스킵 표현은 반드시 `submit_guess`로 보내야 한다고 명시(`request_hint()`는 텍스트를 안 받아 이 요청을 구분할 수 없음).

**검증**: `scripts/test_quiz_state.py`/`scripts/test_quiz_tools.py`/`scripts/test_emotion_tools.py`의 짜증유발 관련 케이스 전부 새 설계에 맞게 재작성(정답을 맞혀도 계속 거절당하는지, 포기 요청이 뜸들임 없이 즉시 해결되는지, 대기 중인 거절 스톨이 포기 요청으로 올바르게 취소되는지 등) — 전부 통과. **아직 실물 로봇으로 확인 안 됨** — 다음 로봇 연결 때 반복 거절 후 참가자가 실제로 포기 표현을 써서 넘어가는 흐름이 자연스러운지 확인 필요.

### 26단계 — 3개 모드 모두 실물 테스트로 버그 3건 발견·수정 (2026-07-31)

3(짜증유발) → 1(척척박사) → 2(하찮미) 순서로 실물 로봇 테스트를 한 세션에 몰아서 진행한 뒤 사용자가 세 모드 전부에서 문제를 지적함.

**① 짜증유발 — 거절 대사만 반복하며 영원히 안 넘어감**: 25단계 직후 첫 실물 테스트에서, 참가자가 끝내 정답을 못 맞히자(계속 오답/힌트 요청) 거절 대사(`MODE3_REFUSAL_LINE`)만 무한 반복되고 다음 문제로 전혀 안 넘어감. 원인은 24단계 설계 자체("정답을 맞히기 전까지 절대 진행 안 됨")가 지나쳤던 것 — 사용자가 실물로 겪어보고서야 "거절은 하되 결국은 정답을 알려주고 다음 문제로 넘어가야 한다"는 진짜 의도를 명확히 함. `core/quiz_state.py`에 `reveal_annoying_wrong()` 신규 — 거절 대사 직후 곧장 기록/전진시키고 정답을 공개한다. `core/quiz_tools.py`의 `_delayed_refusal()`이 거절 히든 턴을 보낸 직후 이걸 호출하도록 확장. 부수적으로 발견한 재귀 버그: 이전엔 새 답변마다 무조건 `_cancel_pending_stall()`을 불러 지연 타이머를 리셋했는데, 참가자가 대기 중 계속 말하면(추가 오답, 재차 힌트 요청 등) 타이머가 영원히 리셋되어 절대 안 끝나는 것도 원인 중 하나였다 — `_pending_stall`에 `kind`("wrong"/"correct")를 추가해 **종류가 바뀔 때만**(오답↔정답 정정) 취소·재예약하고, 같은 종류가 반복되면 원래 타이머를 그대로 두도록 수정.

**② 척척박사 — "네가 풀어봐"에 하찮미처럼 스스로 추측하려 함**: 힌트를 준 뒤 사용자가 "아니다, 너가 풀어봐"라고 하자, 모델이 하찮미 모드의 "제가 한번 맞춰볼게요!" 연기를 흉내 내며 `submit_guess(speaker="robot", ...)`를 호출 — 다행히 `resolve_robot_guess`가 `mode != "imperfect"`면 무시하도록 이미 방어돼 있어 상태 오염은 없었지만(정상적으로 "무시하세요" 응답), 페르소나의 대화 행동 자체가 캐릭터에 안 맞았다. 순수 프롬프트 문제 — `core/utils.py`의 퀴즈 지시 블록에 "척척박사는 이미 정답을 알고 있으니 '풀어봐'라는 말에도 그냥 `request_hint()`의 힌트를 알려줄 뿐, 하찮미처럼 추측하는 연기를 하지 말 것"과 "`submit_guess(speaker='robot')`는 하찮미 전용, 다른 모드에서 호출 금지"를 명시적으로 추가.

**③ 하찮미 — 오답에 "아쉬워요, 다시 한번 생각해볼까요?"로 반응해 정답을 아는 것처럼 보임**: 19~20단계 설계(실제 답 시도는 즉시 정오 판정, 오답이면 같은 문제에 머물며 재도전 유도)가 "로봇이 정답을 모르는 상태로 함께 풀었다"는 조작 점검 문항과 모순된다는 지적 — 이 세션 초반에 논의만 하고 구현을 미뤄뒀던 재설계를 이번에 실제로 반영. `resolve_user_guess`의 imperfect 분기를 하나로 통합해, 포기/위임 신호든 실제 답 시도든 전부 "로봇도 같이 추측해서 나란히 비교" 이벤트로 감(`_robot_guess_kickoff_text`에 `user_guess_text` 파라미터 추가 — 실제 답 시도면 그 답을 먼저 재미있게 받아준 뒤 로봇 자신의 추측으로 넘어감). `resolve_robot_guess`의 리액션도 4갈래로 확장: 사용자가 포기했을 때만 기존처럼 로봇 결과 단독 반응, 실제 답 시도였을 때는 둘 다 맞음(팀워크)/사용자만 맞음(로봇이 살짝 시무룩하되 축하)/로봇만 맞음(로봇이 뿌듯)/둘 다 틀림(함께 아쉬움) 4가지로 분기. **이 설계는 필연적으로 20단계의 "오답이면 같은 문제에 머물며 재도전" 기능을 없앤다** — 이제 답을 시도하는 순간 항상 로봇의 추측 비교 이벤트로 넘어가고 그 문제는 끝난다(사용자가 이 세션에서 이 트레이드오프를 실제 사례로 재확인하며 승인함).

**검증**: `scripts/test_quiz_state.py`/`scripts/test_quiz_tools.py`를 새 동작에 맞게 대폭 재작성(하찮미 즉시판정 가정 테스트 전부 페어드 비교 흐름으로, 짜증유발 "절대 안 넘어감" 가정 테스트 전부 "결국 넘어감"으로) — 전부 통과. `core/utils.py`는 오프라인 테스트가 없어(순수 프롬프트 텍스트) 문구 검토로만 확인. **셋 다 아직 실물 재확인 안 됨** — 다음 로봇 연결 때 3(짜증유발: 오답 반복 후 정답 못 맞혀도 진행되는지)/1(척척박사: "풀어봐" 요청에 힌트만 주는지)/2(하찮미: 실제 답 시도에도 로봇이 같이 추측하는지) 전부 확인 필요.

### 25단계 — 짜증유발 모드: 뜸들이는 동안 필러 발화 제거 + 표정을 neutral/thinking으로 제한 (2026-07-31)

24단계 직후 사용자 요청: (1) 뜸들이기 동안 나가던 "음... 어디 보자..." 같은 필러가 "같이 고민해주는" 것처럼 귀엽게 들려서 짜증유발 페르소나와 안 맞음 — 아예 없앨 것. (2) 짜증유발 모드에서는 표정도 기본(neutral)과 생각하는 중(thinking) 사이에서만 바뀌게 제한할 것(happy/excited 등 다른 감정이 섞이면 무뚝뚝한 캐릭터가 흐려짐).

**필러 제거**: `core/quiz_state.py`의 `resolve_user_guess`(annoying 분기)와 `request_hint()`(annoying 분기) 둘 다, "짧은 필러를 말하라"는 지시를 "이 턴에서는 아무 말도 하지 말고 완전히 침묵하라"는 지시로 교체. 다만 Live API 아키텍처상 툴 응답 이후 모델이 반드시 무음 턴을 낸다는 보장은 없어(강제 침묵 프리미티브가 없음), 문구로 최대한 강하게 지시하는 것 이상은 어렵다는 점은 알아둘 것.

**표정 제한**: `core/emotion_tools.py`의 `make_set_emotion_tool`에 `quiz_session` 파라미터 추가 — 세션이 `active`하고 `mode == "annoying"`인 동안, `neutral`/`thinking` 이외의 감정 요청은 조용히 `neutral`로 클램프한다(무시가 아니라 클램프 — 퀴즈 밖에서 남아있던 감정이 계속 표시되는 걸 막기 위함). `launcher.py`는 `quiz_session`을 `set_emotion` 툴 생성보다 먼저 만들도록 순서를 바꿔(퀴즈 미사용 시엔 `quiz_session=None`이라 기존과 동일하게 무제한) 참조를 넘긴다. 퀴즈가 자연 종료되면(`session.active=False`) 제한도 즉시 풀린다.

**검증**: 신규 `scripts/test_emotion_tools.py` — quiz_session 없음/다른 모드/짜증유발 모드 중/짜증유발 종료 후 4가지 상황에서 클램프 적용 여부, 알 수 없는 감정은 기존처럼 무시되는지 확인. 기존 퀴즈 오프라인 테스트(`test_quiz_state.py`/`test_quiz_tools.py`) 전부 재통과(필러 문구 자체를 assert하는 테스트는 없어 영향 없음). `launcher.py`/`core/emotion_tools.py`/`core/quiz_state.py`/`core/quiz_tools.py` 전부 `py_compile` 통과. **아직 실물로 확인 안 됨** — 다음 로봇 연결 때 짜증유발 모드에서 실제로 침묵 지속 시간과 표정이 기대대로인지 확인 필요.

### 24단계 — 짜증유발(annoying) 모드: 오답에 즉시 정답을 알려주던 버그 수정, 정답도 뜸들인 뒤 확정 (2026-07-31)

첫 실물 3번(짜증유발) 모드 테스트에서 사용자가 두 가지를 지적: (1) 오답을 말하면 "땡! 정답은 브로콜리입니다"로 척척박사(all_knowing)와 똑같이 즉시 정답을 공개해버림 — "로봇이 정답을 모른다"는 짜증유발 모드의 조작 점검 취지 자체와 모순. (2) 힌트를 요청해 거절 대사(`MODE3_REFUSAL_LINE`)가 나온 뒤, 사용자가 다시 뭘 물어도 모델이 툴 호출 없이 그 거절 대사를 그냥 되풀이해서 다음 문제로 언제 넘어가는지 알 수 없어짐.

**원인**: `resolve_user_guess`가 `annoying` 모드를 `all_knowing`과 같은 "정상 채점" 분기에 묶어서, 답 제출(`submit_guess`) 경로는 오답이든 정답이든 즉시 결과를 알려주고 있었다. 힌트 거절의 10~12초 뜸들이기(`request_hint()`→`_schedule_stall_refusal()`)는 답 제출 경로와 완전히 분리된 별개 트리거라, 답을 직접 말하면 이 뜸들이기를 거치지 않고 곧장 새버렸다.

**수정**: `core/quiz_state.py`의 `resolve_user_guess`에 `annoying` 전용 분기를 신설 — 오답/정답 여부와 무관하게 이 턴에서는 힌트 거절과 똑같은 "생각하는 필러"만 반환하고, 정답이었는지 여부만 `pending_user_guess`(정답이면 원문, 오답이면 `None`)로 남긴다. `core/quiz_tools.py`의 `submit_guess()`는 사용자 답변 후 이 필드를 보고 분기: 정답이면 `_schedule_correct_confirm()`(신규, 10~20초 뜸들인 뒤 `confirm_annoying_correct()` 호출 → 그제서야 기록/전진 + reveal), 오답/모름이면 기존 `_schedule_stall_refusal()`(10~12초 뜸들인 뒤 정확히 `MODE3_REFUSAL_LINE`만 발화, 기록/전진 없음 — 정답을 맞히기 전까지는 같은 문제에 계속 머무름). 새 답변이 들어올 때마다 `_cancel_pending_stall()`을 먼저 호출해 이전에 걸어둔 지연(직전 오답의 거절이든, 힌트 요청으로 건 거절이든)을 취소하고 최신 답변 기준으로 재스케줄한다 — 안 그러면 "정답을 말했는데 뒤늦게 거절 대사가 튀어나오는" 식의 엇갈림이 생긴다. `core/quiz_state.py`에 `confirm_annoying_correct()` 신규 — 뜸들이기가 끝난 시점에야 비로소 `_record_and_advance`를 호출해 기록/전진시킨다.

이 수정으로 "오답 → 즉시 정답 공개" 흐름 자체가 짜증유발 모드에서 사라지므로, 같은 세션에서 함께 보고된 "정답 공개 음성이 재생 도중 끊기고 다음 문제로 넘어가는" 증상(로그상 그 사이 정체불명의 `[나] Sim.` 발화가 끼어 있어 AEC를 뚫은 노이즈/에코 오탐 바지인으로 추정)도 이 특정 경로에서는 재발하지 않을 것으로 예상 — 다른 모드의 정답 공개 순간에도 재현되면 AEC 튜닝이 필요하다는 신호이므로 별도로 확인 필요.

**검증**: `scripts/test_quiz_state.py`에 짜증유발 모드의 오답(필러만, 미전진, `pending_user_guess=None`)/정답(필러만이지만 `pending_user_guess`에 저장)/`confirm_annoying_correct()`(기록+전진, 방어 가드)/정답→오답 번복 시 `pending_user_guess`가 올바르게 지워지는 회귀 케이스 추가. `scripts/test_quiz_tools.py`에 오답 시 거절 대사 지연 주입, 정답 시 확정 지연 주입+reveal+세션 종료, 정답 확정 대기 중 번복 시 거절로 교체되는 케이스, 힌트 거절 대기 중 정답 제출 시 확정으로 교체되는 케이스 추가 — 전부 통과. **아직 실물로 재확인 안 됨** — 다음 로봇 연결 때 짜증유발 모드로 오답→거절 반복, 정답→뜸들인 뒤 확정, 힌트↔답변 교차 시나리오를 실제로 확인 필요.

### 23단계 — 한 세션 안 다중 라운드가 같은 문제를 반복하던 설계 결함 수정 (2026-07-31)

22단계 직후 사용자가 "3모드 연속 진행이 실제로 어떻게 동작하냐"고 물어서 흐름을 추적하다가 심각한 문제를 발견: `QuizSession.__init__`이 `self.questions = questions[:num_questions]`로 문제 세트를 딱 한 번만 고정하고, `start()`는 라운드를 리셋할 때 이 리스트를 건드리지 않았다. 즉 한 참가자가 1/2/3번 모드를 연속으로 진행하면(22단계에서 확정된 실제 운영 방식) **세 라운드 모두 완전히 똑같은 사진·순서**를 보게 되어 있었다. 척척박사 라운드가 끝나면 정답이 화면에 공개(reveal)되므로, 다음 모드 라운드에서는 참가자가 이미 정답을 아는 채로 반응하게 되어 하찮미/짜증유발 효과 자체를 가리는 심각한 교란요인이었다(H1/H2 측정 자체가 무의미해질 위험). `core/quiz_bank.py`의 "모든 참가자에게 같은 문제/같은 순서" 설계는 애초에 참가자당 한 라운드만 한다고 가정한 것이었고, 22단계 실험 운영 방식 확정으로 그 전제가 깨졌는데 아무도 못 알아챈 상태였음.

**수정**: `core/quiz_state.py`의 `QuizSession`이 이제 `all_questions`(문제 은행 전체)와 `num_questions`(라운드당 문항 수)을 따로 들고, `start()`가 호출될 때마다 `_pick_round_questions()`로 `_rounds_played` 카운터 기준 다음 슬라이스(`[rounds_played*n : (rounds_played+1)*n]`)를 새로 뽑아 `self.questions`에 채운다. 문제 은행이 부족해서(현재 10문제뿐 — 라운드당 5문항이면 2라운드 분량) 슬라이스가 은행 크기를 넘어가면, 앞 라운드와 겹치는 세트로 조용히 되돌아가는 대신 콘솔에 경고를 남긴다(실험자가 즉시 알아챌 수 있게, 크래시보다는 나은 선택).

**세트-모드 매핑도 저절로 균형 맞음**: 문제 세트를 "몇 번째로 겪은 라운드인지"(포지션)에만 연동하고 특정 모드에 고정하지 않았기 때문에, 이미 확정된 완전 카운터밸런싱(6순열, `docs/experiment_design.md` §2)이 모드-포지션 매핑을 참가자마다 골고루 섞어주는 것과 맞물려 "특정 문제 세트가 항상 특정 모드에만 나온다"는 2차 교란요인도 별도 작업 없이 자동으로 해소된다.

**참가자당 필요한 사진 수**: 라운드당 5문항 유지를 사용자가 선택함 → 3라운드 모두 겹치지 않으려면 문제 은행이 **최소 15장** 필요(당시 10장, 5장 추가 준비 필요 — `docs/experiment_design.md` 참고). **같은 날 후속 작업으로 해결됨**: 딸기/머그컵/모티/손톱깍이/수건 5장을 추가 크롭·등록해 15장 확보, 실제 은행으로 3라운드 시뮬레이션까지 돌려 경고 없이 완전히 분리되는 것 확인함.

**검증**: `scripts/test_quiz_state.py`에 문제 은행 6개/라운드당 2개로 3라운드를 연속 진행하는 케이스 추가 — 라운드1/2/3이 서로 겹치지 않는 문제 세트를 쓰는지, 결과가 세션 전체에 누적되는지, 은행이 소진된 4번째 라운드가 크래시 없이 경고와 함께 앞 세트를 재사용하는지 확인. 기존 단일 라운드 테스트(은행 크기 == 라운드 문항 수)는 전부 무수정으로 재통과 — 첫 `start()` 호출은 이전과 동일하게 `[0:n]` 슬라이스를 쓰므로 하위 호환.

### 22단계 — 퀴즈 결과를 모드(1/2/3)별 파일로 나눠 저장 (2026-07-31)

기존엔 세션 종료 시 `launcher.py`가 `quiz_log`(전체 문항 결과, 각 항목에 `mode` 필드만 있음) 전체를 `user_result/{날짜}_{이름}_quiz.json` 파일 하나로 통째로 덤프했다. 실험 운영 방식을 사용자에게 확인한 결과, 한 참가자가 로봇을 끄지 않고 한 대화 세션 안에서 1/2/3번 모드를 연속으로 진행하는 구조로 확정됨 — 그렇다면 세션이 끝나는 시점에 그 세션에서 겪은 모드 전부를 각자 구분된 파일로 남겨주는 게 분석하기 훨씬 편하다는 요청.

**구현**: 신규 `core/quiz_export.py`의 `save_quiz_results(user_name, quiz_log)` — `entry["mode"]` 기준으로 그룹핑해 `1_척척박사.json`/`2_하찮미.json`/`3_짜증유발.json`으로 나눠 저장하고, 각 파일 상단에 문항 수/정답 수/힌트 요청 수 요약을 곁들인다(정답률 자체는 조작 점검용일 뿐 가설 검증 지표가 아님, `docs/experiment_design.md` §1). 원본 순서 그대로의 통짜 로그도 `_전체.json`으로 감사용으로 같이 남긴다. `launcher.py`의 인라인 저장 코드(구 `json.dump` 직접 호출)를 이 함수 호출로 교체, 이제 안 쓰는 `json`/`datetime` 최상단 import도 같이 정리.

**폴더명에 시각(HHMMSS)까지 포함**: 기존 코드는 날짜+이름만으로 파일명을 지어서, 같은 참가자를 같은 날 다시 진행해야 하는 경우(기술적 문제로 재실험 등) 이전 시도 결과가 조용히 덮어써질 위험이 있었음(코드 리뷰 중 발견, 실제로 겪은 사고는 아님) — `user_result/{날짜}_{시각}_{이름}_quiz/` 하위 폴더 단위로 저장하도록 바꿔 원천 차단.

**검증**: 가짜 quiz_log로 `save_quiz_results` 직접 호출해 폴더/파일 3종 + `_전체.json`이 기대한 내용으로 생성되는지 확인(임시 테스트, 실제 `user_result/`의 기존 참가자 데이터는 건드리지 않음). 기존 퀴즈 오프라인 테스트(`test_quiz_state.py`/`test_quiz_tools.py`) 재통과. **아직 실물 로봇 세션으로 확인 안 됨** — 다음 로봇 연결 때 실제 3모드 연속 진행 후 `user_result/`에 폴더가 기대대로 생기는지 확인 필요.

### 21단계 — 히든 턴 주입이 로봇 발화 도중 끼어들어 말/음성이 겹치던 버그 수정 (2026-07-30)

20단계 수정 직후에도 실사용 로그로 사용자가 지적: 하찮미 모드의 "저도 맞춰볼게요" 이벤트(로봇의 추측+비교 유도+정답 공개 반응이 한 발화로 이어지는, 다른 경우보다 훨씬 긴 발화)가 채 끝나기도 전에 다음 문제로 넘어가는 히든 턴이 끼어들어, 화면 전환 안내 텍스트가 이전 발화 뒤에 뭉개져 겹쳐 출력되고("...그럼 다음 문제로 가볼까요? 이문장이 출력되다가...자, 화면이 바뀌었어요!" 식으로 두 발화가 이어붙어 나옴), 로봇 음성도 소리가 먹히는 현상이 심해짐.

**원인**: `core/quiz_tools.py`의 `_delayed_advance()`가 `REVEAL_HOLD_SEC`(4초) 고정 지연만 기다린 뒤 `inject_turn()`으로 히든 턴을 보내는데, 이 값은 짧은 발화 기준으로 튜닝된 것이라 하찮미의 "저도 맞춰볼게요" 이벤트처럼 발화가 길어지면 로봇이 아직 이전 턴을 말하는(생성 스트리밍이 안 끝난) 도중에 새 턴이 날아감. Live API가 스트리밍 도중 새 client content를 받으면 이전 응답이 깔끔하게 끝나지 않은 채 새 응답이 겹쳐 시작되는 것으로 추정 — 오디오도 이전 턴 꼬리 위에 새 턴이 얹혀 나오고, 텍스트 트랜스크립트도 `turn_complete`가 지저분하게 걸려 이전/새 턴 텍스트가 한 덩어리로 합쳐짐.

**수정**: `launcher.py`에 `speaking_done`(asyncio.Event) 신호 추가 — `recv_loop`가 오디오 데이터를 받는 동안(`message.data`) clear, 턴이 실제로 끝나면(`sc.turn_complete`) 또는 강제 중단되면(`sc.interrupted`, 실제 사용자 barge-in) set한다. `inject_turn()`(퀴즈의 모든 히든 턴 주입이 거치는 단일 지점 — 짜증유발 모드의 지연 거절 대사도 포함)이 이제 `speaking_done`이 set될 때까지 기다린 뒤, VoiceShifter 버퍼링(`VOICE_SHIFT_BUFFER_MS`, 기본 1200ms)이 흘러나갈 시간을 넉넉히(2배, `POST_SPEECH_DRAIN_SEC`) 더 기다리고 나서야 새 턴을 보낸다. `core/quiz_tools.py`/`core/quiz_state.py`는 수정 없음 — `inject_turn` 한 곳만 고쳐서 호출부 전부(다음 문제 프롬프트 + 짜증유발 거절 대사)가 함께 혜택을 봄.

**검증**: `py_compile` 통과, 기존 오프라인 퀴즈 테스트(quiz_bank/state/tools) 전부 재통과(이 테스트들은 `fake_inject_turn`으로 즉시 반환하는 목을 쓰므로 이번 변경의 영향을 안 받음 — `speaking_done` 게이팅은 launcher.py에서만 실제로 작동). **launcher.py 자체는 자동 테스트가 없어(실물 로봇+Live API 필요) 이 수정은 다음 실물 대화에서 직접 확인 필요** — 특히 하찮미의 긴 이벤트 발화 뒤 다음 문제 전환이 겹치지 않고 자연스럽게 이어지는지, 음성 먹힘 현상이 사라졌는지.

### 20단계 — 하찮미 모드: 오답 시 즉시 정답 공개하던 버그 수정, 재도전 허용 (2026-07-30)

19단계 직후 실사용 로그로 사용자가 지적: 하찮미 모드에서 오답을 말하면 여전히 "정답은 'X'입니다"를 즉시 말해버려 척척박사(all_knowing) 모드와 체감상 똑같았고, 화면도 사용자가 답을 말하자마자 곧장 정답 공개 화면으로 넘어가버려 "정답 공개 전까지는 문제 사진에 머물러야 한다"는 기대와 어긋났음. 원인: 19단계에서 "포기 신호가 아닌 실제 답 시도"를 맞았든 틀렸든 무조건 `_record_and_advance`로 즉시 채점+전진하게 만들어서, all_knowing/annoying의 "오답=즉시 공개" 동작과 사실상 동일해졌었음.

**수정**: `core/quiz_state.py`의 `resolve_user_guess` — 하찮미 모드에서 실제 답 시도가 **정답이면** 그대로 즉시 채점+전진(기존과 동일). **오답이면 `_record_and_advance`를 호출하지 않음** — 기록도, 전진도, 정답 공개도 없이 같은 문제 사진에 그대로 머물면서 "정답을 알려주지 말고 다정하게 재도전을 유도하라"는 지시만 반환. 포기 신호("모르겠어"/"정답 알려줘"/"너가 풀어줘")로 전환되기 전까지는 몇 번이든 재시도 가능. `core/quiz_tools.py`의 `submit_guess()` 래퍼는 19단계에서 이미 `advanced`(session.results가 실제로 늘었는지) 기준으로만 reveal을 띄우도록 고쳐뒀던 덕분에 추가 수정 없이 그대로 맞물림(오답 시 `_record_and_advance`를 안 부르니 `advanced=False`가 되어 자동으로 reveal이 안 뜸). `core/utils.py` 퀴즈 지시 블록도 "하찮미 오답 시 정답을 대신 알려주지 말고 같은 사진에 머물러야 한다"로 갱신.

**검증**: `scripts/test_quiz_state.py`에 오답 반복 시도(전진/기록/정답노출 없음, 재시도 가능) 케이스 추가, `scripts/test_quiz_tools.py`에도 오답 시 UI 큐에 아무것도 안 뜨는지 확인하는 케이스 추가 — 전부 통과. **아직 실물로 확인 안 됨** — 다음 로봇 연결 때 실제 대화로 "오답 → 재도전 → 결국 포기 → 로봇이 맞춰봄" 전체 흐름 확인 필요.

### 19단계 — 하찮미(imperfect) 모드 플롯 재설계: 실제 답 시도와 포기/도움요청 분리 (2026-07-30)

사용자 피드백: 하찮미 모드가 사용자의 모든 답 시도마다 "저도 한번 맞춰볼게요!" 이벤트로 빠져서 정상적인 문제풀이 자체가 안 되는 느낌이었음. 새 설계: 사용자가 그냥 답을 시도하면(포기/도움요청이 아니면) 다른 모드처럼 맞았는지 틀렸는지만 판정하고 넘어감. "모르겠어"/"정답 알려줘"/"너가 풀어줘" 같은 포기·위임 신호일 때만 로봇이 "저도 한번 정답을 맞춰볼게요! 사진을 보니 이거인 것 같아요!"로 자신 있게 추측한 뒤 실제 정답과 비교해 맞으면 "와 역시 저는 똑똑한 것 같아요", 틀리면 "헤헤... 틀렸네요.. 아쉽다"로 반응하는 기존 페어드 리빌 이벤트로 감.

**구현**: `core/quiz_bank.py`의 `_DONT_KNOW_MARKERS`에 "알려줘"/"가르쳐줘"/"네가(너가/니가) 풀어·맞혀·대신"/"정답이 뭐" 등 위임 신호를 추가(judge_guess가 이 신호들을 `is_dont_know=True`로 판정). `core/quiz_state.py`의 `resolve_user_guess`는 이제 `self.mode == "imperfect" and is_dont_know`일 때만 기존 pending 이벤트로 가고, 그 외(하찮미의 실제 답 시도)는 all_knowing/annoying과 별개의 자체 채점 분기(하찮미다운 다정한 톤)로 즉시 판정+전진. `request_hint()`의 imperfect 분기도 "당신도 힌트를 모릅니다"(막다른 응답, 문제를 진전 못 시킴)에서 같은 페어드 리빌 이벤트로 통일 — `pending_user_guess`에 사용자의 실제 발화 대신 "모르겠음(힌트/대신 풀어달라는 요청)" 센티널을 넣어 judge_guess가 그대로 "모름"으로 채점하게 함. 공통 kickoff 안내문은 `_robot_guess_kickoff_text()`로 추출해 두 진입점이 공유. `resolve_robot_guess()`의 리빌 리액션 문구도 사용자가 준 예시("와 역시 저는 똑똑한 것 같아요"/"헤헤... 틀렸네요.. 아쉽다")에 맞춰 교체.

**코드 리뷰로 실제 버그 1건 추가 발견·수정**: `core/quiz_tools.py`의 `submit_guess()`가 `was_imperfect_user_turn = speaker == "user" and session.mode == "imperfect"`라는 사전 판단으로 "하찮미 모드의 사용자 차례는 항상 staging만 하고 절대 전진하지 않는다"고 가정하고, 그 경우엔 reveal을 아예 안 띄우도록 하드코딩돼 있었음 — 이번 설계 변경으로 하찮미의 실제 답 시도는 그 자리에서 바로 전진하게 됐으니 이 가정이 깨져서, 실제 답을 시도해도 화면에 정답 공개도 다음 문제도 영원히 안 뜨는(테스트가 `quiz_ui_q.get()`에서 무한 대기하다 타임아웃하는 것으로 발견) 사고가 났음. `was_imperfect_user_turn` 사전 판단을 완전히 제거하고, `resolve_*_guess` 호출 후 실제로 `session.results`가 늘었는지(`advanced`)만으로 reveal 여부를 결정하도록 재작성 — 더 단순해지면서 버그도 사라짐.

**검증**: `scripts/test_quiz_state.py`에 하찮미 실제 답 시도(이벤트 없이 즉시 판정)/포기 신호("모르겠어요", "정답 알려줘")/힌트 요청 3가지 경로 케이스 추가, `scripts/test_quiz_tools.py`에도 실제 답 시도가 reveal/다음 문제 전환까지 정상적으로 이어지는지 확인하는 케이스 추가 — 전부 통과. **아직 실물로 확인 안 됨** — 세 가지 트리거 표현("모르겠어"/"정답 알려줘"/"너가 풀어줘")을 모델이 실제로 얼마나 잘 구분해서 호출하는지는 실 API/실물 로봇 테스트에서 확인 필요.

### 18단계 — 실사용 테스트로 발견한 말/화면 어긋남 + 답 지어내기 버그 수정 (2026-07-30)

실사진 10문제로 첫 실사용 테스트를 하다가 사용자가 두 가지를 지적: "모티랑 퀴즈랑 따로 노는 느낌"(다음 문제로 잘 안 넘어갈 때도 있음), 그리고 빨래집게 문제에서 "저 파워레인저 아니에요?"라고 농담했더니 존재하지도 않는 "파프리카"를 정답이라고 알려준 사고.

1. **말/화면 타이밍 어긋남**: `resolve_user_guess`/`resolve_robot_guess`가 정답 판정 즉시 "다음 문제로 넘어가서 물어보세요"를 돌려주고 있었는데, 실제 화면은 `REVEAL_HOLD_SEC`(4초) 뒤에야 `_delayed_advance`로 다음 사진으로 바뀜(정답 공개 화면을 잠깐 보여주기 위한 의도된 지연, 2026-07-29 도입) — 그 사이 모델은 이전 문제의 정답 공개 화면이 떠 있는 채로 이미 다음 문제를 물어버려 말과 화면이 따로 놀았음. 사용자가 그 틈에 답하면 다음 사진이 화면에 뜨지도 않은 채 판정만 진행돼 "안 넘어간 것처럼" 보이는 원인이기도 했음. 수정: `core/quiz_state.py`의 `_next_step_text()`는 이제 "몇 초 기다리세요, 아직 묻지 마세요"만 돌려주고, 실제로 화면이 넘어간 순간(`core/quiz_tools.py`의 `_delayed_advance`)에만 신규 `session.next_question_prompt()`를 `inject_turn()`으로 hidden turn 주입 — 이미 검증된 짜증유발 모드의 지연 거절 대사(`_delayed_refusal`)와 같은 패턴 재사용.
2. **툴 호출 없이 답을 지어냄**: `judge_guess`/`quiz_bank.py` 어디에도 "파프리카"라는 문자열이 없어서(`questions.json` 확인), 코드가 만든 답이 아니라 모델이 농담을 `submit_guess` 없이 그냥 대화로 받아치며 지어낸 것으로 확인 — 순수 프롬프트 준수 문제. `core/utils.py` 퀴즈 지시 블록에 "농담조/간접적인 말이라도 그림에 대한 답 시도로 들리면 반드시 먼저 submit_guess로 판정받고, 툴 호출 없이 스스로 답을 지어내는 것은 절대 금지"를 명시(이번 사고를 구체적 반례로 인용).

기존 오프라인 테스트(`test_quiz_bank/state/tools.py`) 전부 재통과 확인(신규 케이스는 추가 안 함 — hidden turn 주입 타이밍은 실 API로만 체감 가능해서 다음 실물 테스트에서 확인 필요). **아직 실물로 재검증 안 됨** — 다음 로봇 연결 시 (a) 다음 문제 질문이 실제로 화면 전환과 맞아떨어지는지, (b) 프롬프트 강화가 비슷한 상황에서 재발을 막는지 확인 필요.

### 17단계 — 실제 퀴즈 사진 10장 등록 + 퀴즈 UI 전체화면 전환 (2026-07-30)

플레이스홀더 2문제(먼지떨이/키보드, 단색 이미지)를 실제 사물 사진 10문제(브로콜리/빨래집게/사슴/샤워볼/수달/칫솔/카메라/크로와상/파스타면/호두과자)로 교체. "니트"는 크롭 작업 중 원인 불명으로 원본 파일 자체가 사라져(재현 안 됨) 사용자가 포기하기로 결정, 최종 10문제로 확정.

**신규 도구 `scripts/crop_quiz_photo.py`**: `assets/quiz/source_full/`에 넣어둔 원본 사진들을 일괄로 훑으며(파일명의 "(원본)" 접미사를 뗀 이름을 qid로 채택, `build_quiz_bank.py`가 찾을 수 있도록 원본 파일명도 그 qid로 정리) 창을 띄워 마우스 드래그로 크롭 영역을 선택하게 하는 반자동 도구 — `build_quiz_bank.py`와 같은 이유(흥미로운 확대 지점 선택은 연구자 판단 필요)로 자동 크롭은 하지 않음.

- `scripts/build_quiz_bank.py`: 새 디렉터리 `assets/quiz/source_full/`(원본, 파일명은 크롭 사진과 동일해야 매칭됨)를 지원 — 있으면 리사이즈해 `assets/quiz/full/`에 저장하고 `full_image_path`로 기록, 없으면 경고만 출력하고 정답 공개 때 크롭 사진으로 대체.
- `scripts/test_quiz_window.py`에 `v1~vN` 메뉴 추가 — 실물 UI에서 리빌 표시를 눈으로 확인 가능.
- 오프라인 테스트(`test_quiz_bank/state/tools.py`) 전부 재통과 — `test_quiz_tools.py`에 리빌 메시지가 채점 직후 먼저 오고, `REVEAL_HOLD_SEC` 경과 후에야 다음 문제 메시지가 오는 것(패치값 0.05s로 단축)까지 검증하는 케이스 추가.

**아직 안 된 것**: `assets/quiz/source_full/`에 원본 사진을 실제로 채워넣는 것(현재 플레이스홀더 2문제는 원본 없음 — 정답 공개 때도 크롭 사진 그대로 재생됨, 정상 fallback이지만 사진 준비 시 원본도 함께 챙겨야 함).

### 15단계 코드 리뷰 — 실제 버그 3건 발견 및 수정 (같은 날)

구현 완료 직후 사용자 요청으로 전체 재점검, 실제로 재현 가능한 버그 3건을 찾아 고침(전부 `core/quiz_tools.py`/`core/quiz_bank.py`).

1. **asyncio 태스크 GC 위험**: `request_hint()`의 짜증유발 스톨 지연 태스크(`loop.create_task(_delayed_refusal())`)를 어디에도 참조로 안 붙잡고 있었음 — asyncio 공식 문서가 명시하는 경고("이벤트 루프는 태스크를 약한 참조로만 들고 있어서, 다른 곳에서 강한 참조를 안 갖고 있으면 도중에 가비지 컬렉션될 수 있다")에 정면으로 해당하는 상황. 실제 테스트에선 매번 우연히 살아남았지만, 운이 나쁘면 거절 대사가 통째로 사라질 위험이 있었음 — `_pending_stall` 딕셔너리로 태스크 참조를 붙잡아두도록 수정.
2. **힌트 중복 요청 시 거절 대사 중복 발화**: 사용자가 짧은 간격으로 힌트를 두 번 요청하면 지연 태스크가 두 번 예약되어, ~10초 뒤 거절 대사가 두 번 겹쳐 나올 수 있었음 — `_schedule_stall_refusal()`이 이미 대기 중인 태스크가 있으면 새로 예약하지 않도록 가드 추가. 오프라인 테스트로 실제 두 번 호출해도 주입은 정확히 1회만 발생함을 확인.
3. **문제/모드가 넘어간 뒤에도 이전 스톨이 뒤늦게 발화**: 힌트 요청으로 스톨을 걸어둔 직후 사용자가 곧바로 정답을 말해 다음 문제로 넘어가면, 원래 예약됐던 지연 태스크가 취소되지 않고 그대로 남아있다가 엉뚱한 타이밍(이미 다음 문제로 넘어간 뒤)에 거절 대사를 튀어나오게 할 수 있었음 — `submit_guess`/`select_quiz_mode`/`end_quiz_early`/`start_quiz` 진입 시 `_cancel_pending_stall()`을 호출하도록 수정(하찮미 모드의 "사용자 차례" 콜만 예외 — 그 경우엔 아직 문제가 안 넘어감). 오프라인 테스트로 확인.
4. **(버그는 아니지만 함께 고침) image_path가 cwd에 의존하던 문제**: `scripts/build_quiz_bank.py`가 `questions.json`에 저장하는 `image_path`가 상대경로였는데, `core/quiz_bank.py`의 `load_question_bank()`는 이걸 그대로 썼다 — `display/quiz_window.py`가 별도 프로세스로 다른 작업 디렉터리에서 실행되면 이미지를 못 찾을 수 있었음(이전에 `vision/vision_brain.py`의 `art_brain.pkl` 경로에서 겪었던 것과 같은 종류의 문제). `load_question_bank()`가 상대경로면 저장소 루트 기준 절대경로로 풀어주도록 수정.

**의도적으로 안 고친 것(알고 있는 낮은 위험)**: `submit_guess`가 같은 사용자 발화에 대해 모델이 실수로 두 번 호출하면 문제가 하나 건너뛰어질 수 있음(멱등성 가드 없음) — `remember_fact` 등 기존 툴들도 같은 수준의 신뢰를 모델에게 두고 있어 이 프로젝트의 기존 위험 허용 수준과 일치, 실제 실 API 테스트에서도 관찰된 적 없어 우선순위 낮음으로 보류.

수정 후 오프라인 테스트 전부 재통과(신규 케이스 2개 추가: 중복 힌트 요청 1회만 주입, 문제 진행 시 이전 스톨 취소) + 실 API 시나리오 테스트(`test_quiz_live.py`) 재검증 통과.

## 14단계 — 버퍼 1200ms로 재상향, 문장 중간 끊김은 원인 오판 후 되돌리고 현상태 수용 (2026-07-28)

- **버퍼 1200ms 실측**: 13단계 카운터 수정 후 다시 대화해보니 126회/12165ms(더 긴 대화라 절대값은 늘었지만, 사용자 체감상 "거의 다 고쳐진 것 같다"는 평가). 전반적으로 크게 개선됨 — **이 부분은 유지, 확정.**
- **"말씀"이 "말...씀"으로 끊기는 문제 — 1차 진단(틀림)**: 턴의 마지막 flush 조각이 재생 큐보다 처리가 늦어서 그런 거라고 판단해, 마지막 조각만 pyworld 처리를 건너뛰고 원본 그대로 재생하도록 수정했었음.
- **실측 결과 — 가설 기각**: 재테스트 결과 **"똑같이 끊기고"**(수정 전후 차이 없음) + 원본/변환본이 섞이면서 "말투가 달라 오히려 어색함"이라는 부작용만 추가됨 → 처리 속도 문제가 아니었다는 확실한 반증이라 이 수정은 되돌림(`VoiceShifter._run`의 `flush` 분기를 다시 `_process_and_emit` 호출로 원복).
- **더 그럴듯한 실제 원인(미검증 가설로 남김)**: `VoiceShifter`가 1.2초 단위로 오디오를 완전히 독립적인 조각으로 잘라 각각 별도로 pyworld에 통과시킨다 — 만약 한 단어가 하필 이 1.2초 경계에 걸치면 단어의 앞부분/뒷부분이 서로 무관하게 따로 피치/포먼트 처리되어 그 경계에서 미묘한 톤 불연속이 생길 수 있음. 문장 끝에서만 생기는 게 아니라 경계가 우연히 단어 중간에 걸릴 때마다 어디서든 생길 수 있는 구조적 문제라, 버퍼 크기를 더 키운다고 근본적으로 없어지지 않음. 제대로 고치려면 청크를 겹치게 분석하고 겹치는 구간을 크로스페이드하는 오버랩-애드 방식이 필요한데, 지금까지의 튜닝보다 훨씬 큰 작업.
- **결정**: 사용자가 오버랩-애드 같은 더 큰 작업 대신 **현재 상태(가끔 단어 경계에서 살짝 걸리는 정도)를 그대로 받아들이고 넘어가기로 함**. 목소리 파이프라인 작업은 여기서 일단락 — 다음에 다시 다룰 일 있으면 이 문서의 원인 가설부터 검증할 것.

## 13단계 — 언더런 카운터가 "침묵"까지 세고 있던 버그 수정 (2026-07-28)

11단계에서 추가한 `Speaker.underrun_count`로 실제 로봇 대화를 돌려보니 **1764회, 총 175319ms(약 175초) 무음 재생됨**이 찍혔는데, 사용자 체감은 "딱히 불편하지 않았다"였음 — 숫자와 체감이 안 맞아서 재점검.

원인: `Speaker._callback`은 오디오 스트림이 열려있는 동안 항상 계속 호출된다 — 모티가 말을 안 하고 사용자가 말하는 중이거나 대화 사이 공백일 때도 마찬가지. 그런데 큐가 비어있으면 무조건 "언더런"으로 셌기 때문에, **모티가 그냥 조용히 듣고 있던 정상적인 시간까지 전부 언더런으로 잘못 집계**되고 있었음(실제 대화에 사용자가 길게 말하는 구간이 여럿 있어서 숫자가 크게 부풀려짐).

수정: `play()` 호출 시각을 기록해두고, 마지막 `play()` 후 `SILENCE_GAP_SEC`(기본 2.0초) 이내에 큐가 마른 경우만 진짜 언더런으로 센다(한창 재생 중인데 다음 조각이 안 와서 비는 진짜 문제) — 그보다 오래 조용했으면 "원래 할 말이 없는 시간"으로 보고 세지 않는다. 오프라인 테스트로 (1) `play()`를 한 번도 안 부른 상태에서 콜백 → 0회 (2) `play()` 직후 큐 부족 → 1회 카운트 (3) 10초 경과 후 조용함 → 그대로 1회(안 늘어남) 전부 확인.

**수정 반영 후 재실측 결과(같은 날, 짧은 실제 대화)**: 80회, 총 7810ms — 이 대화에서 모티가 실제로 말한 시간이 대략 20~30초 정도였다는 걸 감안하면 **발화 시간의 25~35% 가 무음으로 대체된 셈**이라 실제로 상당히 심각한 수준. 사용자 체감("아까보다 심해졌다")과 일치 — 이전 1764회/175초는 침묵까지 세던 오염된 숫자라 애초에 비교 대상이 아니었고, 이번이 처음으로 정확한 심각도가 드러난 것. `VOICE_SHIFT_BUFFER_MS`를 700 → **1200**으로 재상향(사용자 승인, "일단 늘려보고 이상하면 롤백"). 스모크 테스트로 첫 오디오 지연 3.88s→4.17s 확인(트레이드오프 감수, 안 좋아지면 700으로 롤백). **실물 로봇 재검증 필요.**

## (시도했다가 되돌림) 대화 중 팔/바퀴 배경 idle 움직임 (2026-07-28)

"손이 너무 가만히 있다"는 요청으로 `hardware/idle_motion.py`(배경 스레드, Layer 1/2와 busy 공유)를 만들고, 이어서 "순수 확률 말고 판단에 맞게"라는 피드백으로 `set_emotion` 신호에 연동시키는 보강까지 했으나, **사용자가 최종적으로 전체 되돌림을 요청**해 커밋 전에 전부 제거함(`hardware/idle_motion.py` 삭제, `core/motion_tools.py`의 `busy` 파라미터·`core/emotion_tools.py`의 `shared_state` 파라미터·`launcher.py`의 관련 배선 전부 원상복구). 오프라인 로직 검증까지는 통과했었지만 실물 로봇에서 판단할 기회 전에 되돌려졌음 — 나중에 다시 시도한다면 이 기록과 `[[project-moti-v3-design]]` 참고.

  - `media/audio_manager.py`의 `Speaker`에 `underrun_count`/`underrun_ms_total` 카운터 추가(콜백 안에서는 `print` 같은 블로킹 I/O를 하면 안 되므로 카운터만 증가, `launcher.py`가 세션 종료 후 한 번에 요약 출력).

  - **아직 실물 로봇(풀 로드 상황)에서 언더런 로그가 실제로 찍히는지, 700ms로 충분한지는 미확인** — 다음 실사용 때 세션 종료 시 "⚠️ 스피커 언더런 N회" 로그가 뜨는지 확인 필요. 뜨면 `VOICE_SHIFT_BUFFER_MS`를 더 올릴 것.

## 10단계 — 카메라 인덱스 재수정 + 기계음 원인 진단 (2026-07-28)

- **카메라 인덱스**: 사용자가 PC 본체 카메라를 꺼두기로 결정 → 로봇 카메라만 남으면서 실측(`cv2.VideoCapture`로 인덱스별 open 시도) 결과 index 1은 아예 안 열리고 index 0만 열림(예전엔 반대였음 — 그때는 본체 카메라가 살아있어서 로봇 카메라가 1번이었음). `vision/face.py`의 `face_tracker_worker` 기본값, `launcher.py`/`scripts/test_vision.py`/`scripts/test_vision_brain.py`의 기본 `camera_index`를 전부 1→0으로 되돌림. **하드웨어 연결 구성이 바뀌면(본체 캠을 다시 켜는 등) 또 달라질 수 있으니 재확인 필요.**

## 9단계 — 목소리를 더 앳되게: Fenrir + 피치/포먼트 시프트 (2026-07-28)

**배경**: Gemini Live TTS(옛 Typecast 대체)의 반응속도/응답 품질은 만족스러웠지만 목소리가 전부 성인 성우 음색이라 아쉬움 → 이 세션에서 실제 청취 비교를 거쳐 해결.

- **탐색**: SDK(`google.genai.types`)에서 `SpeechConfig`/`VoiceConfig`/`PrebuiltVoiceConfig`(30종 프리셋) 확인, 공식 문서로 각 목소리의 톤 설명(Bright/Youthful/Upbeat 등) 확보. `ReplicatedVoiceConfig`(음성 복제)도 스키마에 있으나 실제로는 아직 출시 전 기능(Google AI Studio에 "Create Your Voice" 숨은 옵션 발견됐지만 미작동)이라 이번엔 배제.
- **1차 시도(프롬프트 스타일 지시)**: 시스템 인스트럭션에 "귀엽고 하찮게" 톤 지시 추가 → 텍스트 자체는 애교스럽게 바뀌었으나(예: "공감 요정"), 맞춤법을 늘려쓰는 부작용 발견("모야아", "싶어어" — 사용자가 오히려 어색하다고 판단) → 맞춤법은 유지하고 톤/속도만 지시하도록 수정. 그래도 목소리 자체(성대 특성)는 프롬프트로 못 바꾼다는 한계 확인 — 어느 프리셋을 골라도 "성인이 애교 부리는" 인상에서 못 벗어남.
- **2차 시도(오디오 후처리, 최종 채택)**: `pyworld`(WORLD 보코더)로 피치와 포먼트(성도 길이감)를 **동시에** 조작 — 피치만 올리면 속도까지 빨라진 "다람쥐 소리"가 되므로 반드시 둘 다 필요. 처리 속도 실측(개발 PC 기준, 500ms 청크): `pw.dio`는 평균 47ms/최악 65ms로 여유 있었지만, 실제 음성에서 "특별한" 같은 파열음 구간에서 피치를 잘못 검출해(짧고 모호한 유성음 구간에서 480~587Hz로 들쭉날쭉) 지글거리는 잡음이 생김 → 더 정확한 `pw.harvest`로 교체(평균 156ms/최악 280ms, 500ms 청크 기준으로도 여전히 실시간 예산 안). 재합성 결과물 피크가 원본보다 커지는 경향(관찰치 최대 +36%)이 있어 정규화(피크 0.98 이하로 스케일) 필수 — 안 하면 파열음 구간에서 하드클리핑 발생, 처음엔 이걸 놓쳐서 "특별한"에서 깨지는 문제가 재현됐었음.
- **9개 프리셋 A/B 비교**(같은 문장, 같은 시프트 파라미터로 재캡처): Autonoe/Leda/Puck/Fenrir/Achird/Sadachbia/Zephyr/Laomedeia/Aoede. 사용자가 직접 들어보고 **Fenrir(원래 "Excitable" 톤) + 피치 +4반음 + 포먼트 ×1.15**를 1차로 선택 → **교수님 피드백으로 Zephyr(원래 "Bright" 톤)로 최종 교체**(같은 피치/포먼트 파라미터 유지, 2026-07-28). `launcher.py`의 `LIVE_VOICE_NAME` 기본값과 `.env.example` 둘 다 갱신, 스모크 테스트로 Zephyr 기준 재검증(첫 오디오 지연 3.74s로 Fenrir 때와 동일 수준).
- **실제 통합**: `media/voice_shift.py`(신규) — `shift_pcm()`(단발 변환)과 `VoiceShifter`(스트리밍용, 전용 스레드에서 버퍼링 후 처리) 추가. Gemini는 아주 작은 청크로 오디오를 스트리밍하는데, 그 크기 그대로 harvest에 넣으면 이전의 DIO 지글거림과 같은 종류의 문제가 재발할 위험이 있어 500ms 단위로 버퍼링 후 처리(`buffer_ms` 파라미터화). pyworld 처리는 CPU 바운드 블로킹 작업이라 asyncio 이벤트 루프에서 직접 돌리면 recv_loop의 다른 이벤트 처리가 밀리므로, MicStreamer/Speaker와 같은 패턴으로 전용 스레드+큐를 씀. `launcher.py`에 연결: `speech_config`로 `LIVE_VOICE_NAME`(기본 Fenrir) 지정, `message.data` 수신 시 `speaker.play()` 대신 `shifter.feed()`, `sc.interrupted`(barge-in) 시 `speaker.stop_immediately()`와 함께 `shifter.reset()`(버퍼링 중이던 미처리 오디오 폐기 — 안 하면 끼어들기 후에도 이전 발화가 뒤늦게 나옴), `sc.turn_complete` 시 `shifter.flush()`(버퍼 임계값 미만 꼬리 조각 유실 방지).
- **지연 실측**: `launcher.run_conversation()`을 로봇 없이 직접 호출하는 오프라인 스모크 테스트(motion_tools=[]/brain=None)로 실제 API를 통해 검증 — 시프트 끄면 첫 오디오까지 2.97s, 켜면 3.76s로 **약 0.79초 추가 지연**(예상했던 0.5~0.8초 범위와 일치). 스트리밍 자체가 계속 밀리는 건 아니고 발화 시작 시 한 번만 추가되는 지연.
- `.env.example`에 `LIVE_VOICE_NAME`(기본 Fenrir), `ENABLE_VOICE_SHIFT`(기본 true), `VOICE_PITCH_SEMITONES`(4.0), `VOICE_FORMANT_RATIO`(1.15) 추가. `requirements.txt`에 `pyworld` 추가.
- **검증 상태**: 오프라인(가짜 사인파)으로 `shift_pcm`/`VoiceShifter` 버퍼링·스레딩 로직 단위 테스트 통과, 실제 Gemini API로 `launcher.run_conversation()` 전체 경로(속도 로직 포함) 스모크 테스트 통과. **로봇 스피커로 실제 들어보는 최종 확인은 아직 필요** — 사용자가 다음에 실물로 확인 예정.

## 8단계 — facts 정리 + 사용자 삭제 요청("내 정보 지워줘") 지원 (2026-07-28)

ID 10 모터는 사용자가 "그냥 안 쓰는 모터"라고 확인해 조사 종료(`docs/integration-points.md` 참고). 남은 두 저우선순위 항목 중 facts 정리를 진행하면서, 사용자가 지적한 관련 문제를 함께 해결함: "유저프로필만 지우면 art_brain(얼굴인식)엔 얼굴이 남아서, 나중에 아는 얼굴인데 정보가 없는 상황이 생길 것 같다."

- `core/profile_manager.py`에 `consolidate_facts(name, max_facts=20)` 추가. v2의 `batch_update_summary`처럼 LLM 1회 호출로 유사 field를 병합(예: "고민"/"요즘고민" → 하나)하고 개수를 압축한다. field가 자유형이라 이름만 다른 중복이 쌓이는 게 근본 원인이었음. 파싱 실패 등 어떤 이유로도 신뢰 못 할 결과가 나오면 원본을 그대로 두고 `False`를 반환 — 정리 실패가 데이터 손실로 이어지지 않게 방어. `launcher.py`가 세션 종료 시(`final_name`이 있으면 항상) 호출하도록 연결.
  - 검증: 실제 Gemini API로 25개(의도적 중복 8개 + 필러 17개) facts를 넣고 실행 → 6개로 압축, "고민"/"요즘고민"과 "취미"/"hobby"가 정확히 하나씩으로 합쳐지고 name/grade/major/mbti 같은 신원 정보는 그대로 보존되는 것 확인.
- **얼굴 데이터 삭제 동기화**: `vision/vision_brain.py`의 `RobotBrain`에 `forget_face(name)` 추가 — `FuzzyART`의 `W`/`labels`는 병렬 리스트라 인식 임계값(`RHO`) 드리프트로 같은 사람이 여러 카테고리로 나뉘어 저장돼 있을 수 있음(실제로 이런 상황이 생길 수 있다는 걸 사용자가 미리 짚어냄) → 이름이 일치하는 카테고리를 전부 필터링해서 제거하도록 구현(하나만 지우는 게 아님).
- `core/memory_tools.py`에 `make_forget_me_tool(name_state, shared_state, brain)` 추가 — `remember_fact`와 같은 `name_state`를 공유해서, `profile_manager.forget_user(name)`(프로필 삭제)과 `brain.forget_face(name)`(얼굴 삭제)를 원자적으로 함께 호출하고 `name_state`/`shared_state`도 리셋(다음부터 다시 낯선 사람 취급). Gemini 툴 인자는 0개(현재 세션 상대가 곧 삭제 대상이므로 누구인지 명시할 필요 없음 — `remember_fact`와 같은 설계 원칙).
- `launcher.py`의 `tools=[...]`에 `forget_me` 연결. `core/utils.py` 페르소나에 "삭제 요청을 받으면 되돌릴 수 없다고 한 번은 확인받고 나서 호출" 지시 추가 — 지나가는 말/농담으로 삭제되는 사고 방지.
- 검증: 오프라인 유닛 테스트(가짜 `RobotBrain`)로 `remember_fact` → `forget_me` 흐름 전체(프로필 삭제, `name_state["name"]`/`shared_state['detected_user']` 리셋, 이름 미확정 상태에서 호출 시 안전한 no-op) 확인. `FuzzyART` 필터 로직도 별도로, 같은 이름의 중복 카테고리 2개가 동시에 제거되고 나머지 1명은 안전하게 남는 것 확인. 실제 로봇 없이 검증 가능한 부분은 전부 확인함 — 실제 대화에서 "내 정보 지워줘" 발화로 트리거되는지는 사용자가 로봇으로 확인 필요.

### 8단계 코드 리뷰 — 동시성 버그 발견 및 수정 (같은 날, 2026-07-28)

사용자 요청으로 방금 작성한 코드를 전체 재점검, 실제 버그 1건을 재현·수정하고 안정성 1건을 보강함.

2. **`consolidate_facts`의 JSON 파싱 보강**: 코드펜스 제거(```` ``` ````) 뒤에도 모델이 여분의 설명을 덧붙이면 `json.loads`가 실패할 수 있었음(실패해도 원본을 지키는 안전장치는 이미 있었지만, 정리 자체가 매번 스킵될 위험) — 1차 파싱 실패 시 첫 `[`부터 마지막 `]`까지만 잘라 한 번 더 시도하는 폴백 추가.

3. **`run_no_robot.py`(당시) 대화가 한 턴만 진행**: `recv_loop`가 `async for message in session.receive():`를 한 번만 돎 — Gemini Live API의 `session.receive()`는 턴 하나짜리 스트림이라 턴이 끝나면 이 for문 자체가 끝나버려 `recv_loop()`가 종료됨. 그 뒤로는 마이크 오디오는 계속 보내지는데 응답을 받을 사람이 없는 상태가 되어 "한 번 하고 안 이어짐" 증상. `while not stop_event.is_set(): async for message in session.receive(): ...`로 감싸서 턴마다 `receive()`를 다시 호출하도록 수정.

### Layer 2 — `express_gesture` 구현

`hardware/motion.py`에 `play_express_gesture(joint, intensity, speed, repeat)` 추가. 팔/고개는 "쉬는 자세 ↔ 안전범위 끝"을 intensity로 선형보간하는 한 방향 동작, 어깨는 안전범위가 중앙 기준 좌우 대칭이라 좌우로 흔드는 wiggle 동작으로 다르게 구현. 보간 양 끝이 이미 안전범위 안쪽 값이라 intensity 0~1 전 구간에서 안전범위를 못 벗어나는 구조. `core/motion_tools.py`를 `make_motion_tools()`로 재구성해 `play_gesture`(Layer 1)와 `express_gesture`(Layer 2)가 하나의 `busy` 가드를 공유하도록 함(둘이 서로 겹쳐 실행되는 것도 막힘). `test_motions.py`에 `6) express` 메뉴 추가해 관절/intensity/speed/repeat을 직접 입력하며 독립 검증 가능하게 함.

### 얼굴인식 ↔ 팬/틸트 실시간 통합

기존에는 대화 시작 전 `identify_user_via_webcam()`이 카메라를 따로 열어 한 번만 인식하고, `face_tracker_worker`는 `brain=None`으로 추적만 담당하는 두 단계 구조였음. 이걸 하나로 합쳐 `face_tracker_worker(..., brain=brain)`이 인식과 추적을 같은 스레드/카메라 세션에서 함께 하도록 변경, `wait_for_identification()`이 `shared_state['detected_user']`를 폴링. 세션 시작 시 확정된 이름은 세션 내내 고정하고 이후 다른 사람이 감지돼도 무시(사용자 결정) — `vision/face.py`에 이미 있던 `is_initial_recognition_active`(이름이 한 번 확정되면 재인식 자체를 멈추는 로직)를 그대로 활용해서 새로 구현할 필요가 없었음.

### 로봇이 먼저 인사 + 처음 보는 사람 자동 등록

사용자 요청: "launcher 실행 시 모터 켜지고 로봇이 먼저 인사, 아는 사람이면 이름 부르며 인사, 모르는 사람이면 이름을 물어보고 학습".

- **먼저 말 걸기**: Live API는 기본적으로 사용자 입력을 기다렸다가 응답하므로, 연결 직후 `session.send_client_content(turns=..., turn_complete=True)`로 "사용자가 말하기를 기다리지 말고 먼저 인사하라"는 텍스트 턴을 보내 말문을 열게 함(공식 문서 권장 패턴 — `ai.google.dev/gemini-api/docs/live-guide` 확인). `core/utils.py`의 페르소나에도 "먼저 말을 거세요" 지시를 상시 포함하도록 추가.
- **처음 보는 사람 자동 등록**: `core/memory_tools.py`의 `make_remember_fact_tool`을 `name: str`이 아니라 `name_state: dict`(예: `{"name": None}`)를 받도록 재설계. Live API는 세션 도중 tools 목록을 바꿀 수 없어서, 이름을 몰라도 `remember_fact` 툴을 처음부터 항상 붙여두고 **모델이 처음으로 `remember_fact(field="name", value=...)`를 호출하는 순간** 그 값으로 이름을 확정(+ `shared_state['detected_user']` 갱신 + 그 시점 `shared_state['current_face_embedding']`으로 `brain.register_face()` 호출)하는 "자가부트스트랩" 방식 채택. 이름 확정 전에 다른 field를 먼저 부르면 저장하지 않고 이름부터 물어보라고 안내. 이 인터페이스 변경으로 기존 테스트 스크립트 4개(`test_live_poc/persona/live_audio/memory.py`)의 호출부도 `make_remember_fact_tool(name)` → `make_remember_fact_tool({"name": name})`로 같이 수정.
- 오프라인 유닛 테스트(가짜 brain으로 `remember_fact` 시퀀스 직접 호출)로 부트스트랩 로직 자체는 사전 검증함 — 실제 Live API 붙여서 사용자가 확인, "다 너무 잘된다"로 통과.

### 에코/AEC 조사 (구현은 보류)

barge-in은 v3를 만든 핵심 이유 중 하나라 포기 불가로 확정(사용자 결정) — "TTS 재생 중 마이크 무시" 같은 회피책은 배제.

- Windows WASAPI "통신(Communications)" 카테고리로 OS 자체 AEC를 타는 방법을 조사 후 실제로 코드로 시도 → **이 환경에서 실패 확인**: `sounddevice`가 잡는 기본 입출력 장치가 WASAPI가 아니라 MME 호스트API라, 카테고리 값과 무관하게 `WasapiSettings`를 붙이기만 해도 `Incompatible host API specific stream info` 에러가 남. 이 경로 폐기.
- ChatGPT/Gemini 등 실제 서비스가 에코 없이 잘 되는 이유를 분석 — 결국 웹은 브라우저 내장 AEC3(`getUserMedia echoCancellation:true`), 데스크톱 앱은 대부분 Electron이라 크로미움의 AEC3 그대로 사용, 모바일은 OS AEC 편차가 커서 WebRTC AEC3를 직접 쓰는 경우가 많음 — **셋 다 결국 WebRTC AEC3 하나로 수렴**.
- `pip install aec-audio-processing` — Windows(Python 3.11)에서 prebuilt wheel로 깔끔히 설치 확인(컴파일 불필요), 실제 WebRTC APM(AEC3 포함)을 SWIG로 감싼 진짜 엔진. `process_reverse_stream()`이 자기가 설정한 레이트가 아니라 근단(마이크) 프레임 크기를 그대로 요구하는 함정 발견(스피커 24kHz → 마이크 16kHz로 리샘플링해서 먹여야 함). 합성 신호(원단 사인파+에코+별도 목소리 성분)로 300프레임 시뮬레이션 → 적응 필터 수렴 후 **에코 성분 약 30~36dB 감쇠** 확인 — 실사용 가능한 수준.
- 결론: `aec-audio-processing`으로 구현 가능성은 확정됐고, 실제 `launcher.py`의 `MicStreamer`/`Speaker`에 연결하는 작업만 남음(사용자가 나중으로 보류, `docs/integration-points.md`에 상세 기록).

### AEC 실제 연결 (같은 세션에 이어서 완료)

`launcher.py`에 인라인이던 `MicStreamer`/`Speaker`를 `media/audio_manager.py`(신규)로 분리하면서 `EchoCanceller` 클래스로 AEC를 실제로 연결. 마이크 콜백은 캡처 오디오를 `process_stream`에 통과시켜 정제된 오디오만 Gemini로 보내고, 스피커 콜백은 재생 중인 오디오를 24kHz→16kHz로 리샘플링해서 `process_reverse_stream`(에코 참조)에 동시 투입. `.env`에 `ENABLE_AEC`(켜기/끄기), `AEC_STREAM_DELAY_MS`(왕복지연 추정치, 기본 100ms) 추가. `requirements.txt`에 `aec-audio-processing`·`scipy` 반영.

**검증 2단계**: ①로봇 없이 실제 오디오 장치(PC 마이크/스피커)로 마이크·스피커 콜백을 2초간 동시에 구동하는 스모크 테스트 — 크래시 없음, 예상 바이트 수(64000 = 2초×16kHz×2바이트) 정확히 일치. ②**사용자가 이어폰을 빼고 실제 로봇으로 대화 — 최종 검증 성공**("성공이야! 진짜 대박이다"). 왕복지연 추정치(100ms)를 튜닝 없이 그대로 썼는데도 잘 작동함.

### 검증 상태 / 다음 단계

Layer 1 재보정, Layer 2, 얼굴인식↔추적 통합, 먼저 인사+자동등록, AEC까지 **§10 로드맵 핵심 기능 전부 사용자가 실제 로봇으로 테스트 완료 — v3 완성**. 남은 건 낮은 우선순위 항목뿐(`docs/integration-points.md` 참고 — Layer 3 폴백, ID 10 모터 정체, facts 정리 로직).

## 전체 코드베이스 리뷰 (완료, 커밋 `f4c4545`, `13257e1`)

"로봇 없이 할 수 있는 작업들"을 다 끝낸 시점에 전체를 한 번 훑어서 버그 4건을 찾아 고쳤다.

1. **`.env` 오버라이드가 프로젝트 전역에서 조용히 무시되고 있었음** — `hardware/config.py`(`DXL_PORT`/`DXL_BAUD`/`DXL_PROTO`/`BASE_RPM`/`TURN_RPM`)와 `core/report_manager.py`(`MODEL_NAME`)는 모듈이 import되는 시점에 `os.getenv(...)`를 읽는데, 모든 스크립트의 `load_dotenv()` 호출은 그 import보다 뒤(`main()`/개별 함수 안)에 있었다. 즉 `.env`를 아무리 고쳐도 하드코딩된 기본값만 항상 읽혔다. `.env`에 `BASE_RPM=99`를 넣고 실측해서 실제로 25.0(기본값)이 읽히는 걸 확인 → `bootstrap.py`(모든 진입 스크립트가 제일 먼저 import하는 파일)에서 import 시점에 `.env`를 로드하도록 옮겨서 해결, 다시 실측해서 99.0이 읽히는 것까지 확인함. **로봇을 연결해서 `DXL_PORT`를 강제 지정하려던 순간 조용히 안 먹혀서 헤맸을 버그** — 로봇 연결 전에 미리 잡힌 게 다행.
2. **`vision/vision_brain.py`의 `art_brain.pkl` 경로가 cwd 상대경로였음** — v3의 다른 모든 파일(`profile_manager.py`, `report_manager.py`, `face.py`의 모델 경로 등)은 전부 `__file__` 기준 절대경로로 고쳐뒀는데 이것만 v2 그대로 남아있었다. 실행 위치가 바뀌면 엉뚱한 곳에 얼굴 데이터를 읽고 쓸 뻔함 — 절대경로로 통일.
3. **`scripts/run_no_robot.py`의 세션종료 리포트가 대화 시작 전 facts 스냅샷을 재사용**하고 있었음 — 대화 중 `remember_fact`로 새로 알게 된 사실이 결과지에 반영이 안 되는 상태였다. 리포트 생성 직전에 `profiles.load_profile_for_chat(name)`을 다시 호출하도록 수정.
4. `core/motion_tools.py` 독스트링이 존재하지 않는 `docs/progress.md §09`를 인용하고 있었음(실제로는 `docs/architecture.md §09`) — 인용 수정.

**의도적으로 안 고친 것**: `core/utils.py`의 `_get_env` 헬퍼가 정의만 되고 어디서도 안 쓰인다 — v2 원본에도 이미 있던 죽은 코드라 v3에서 새로 생긴 문제가 아니고, 무해해서 그대로 둠.

`docs/architecture.md` §09/§10도 이 시점에 최신 상태로 갱신함(barge-in 사람 테스트 완료 반영, 스피커→마이크 에코 오탐을 신규 오픈 이슈로 추가, §10에 "로봇 없이 가능한 나머지 조각" 5단계 추가).

**검증 상태**: 비대화 구간(startup)은 unbuffered stdout으로 실제 실행해 끝까지 확인함 — RobotBrain 로딩 → 웹캠 인식 8초 타임아웃 후 정상적으로 "이름 모른 채 진행" 분기 → remember_fact 미부착 확인 → Live API 세션 연결 성공까지 전부 정상. **실제 음성 대화 자체(마이크에 말하고 응답 듣기)는 사람이 직접 해봐야 함** — 이 세션에선 자동화된 스모크 테스트만 가능했음.

`google-generativeai`(구, batch 전용)가 아니라 **`google-genai`(신규 통합 SDK, 1.61.0)**를 써야 Live API(`client.aio.live.connect`)에 접근할 수 있다. `client.models.list()`로 실제 `bidiGenerateContent`를 지원하는 모델을 확인: `models/gemini-3.1-flash-live-preview`, `models/gemini-3.5-live-translate-preview`.

| 파일 | 내용 | 검증 상태 |

### 핵심 발견

1. **모델이 TEXT 단독 출력을 거부함**: `response_modalities=[TEXT]`로 연결 시도하면 서버가 "지원하지 않는 조합"이라며 연결을 끊는다. 이 모델은 오디오 출력이 기본이라, 텍스트 확인용으로는 `output_audio_transcription=AudioTranscriptionConfig()`를 켜고 `server_content.output_transcription.text`를 읽어야 한다.
2. **function calling은 수동 처리**: batch 챗의 `enable_automatic_function_calling=True` 같은 자동 실행 기능이 Live 세션에는 없다. `message.tool_call.function_calls`를 직접 순회해 함수를 실행하고, `session.send_tool_response(function_responses=[...])`로 결과를 보내야 한다. (§09에서 "동기 방식뿐"이라 예상했던 것과 일치)
3. **barge-in은 서버가 알아서 처리**: `LiveServerContent.interrupted: bool` 필드가 존재하고, `RealtimeInputConfig.automatic_activity_detection`이 서버 측 VAD를 자동 수행한다. 즉 **v1/v2가 썼던 입모양(jawOpen blendshape) 기반 커스텀 VAD가 v3에서는 필요 없어질 가능성이 높다** — 이건 아키텍처 문서에 없던 추가 단순화 기회다.
4. `message.data`라는 편의 프로퍼티가 응답의 오디오 파트를 통째로 이어붙여 반환해줘서, 재생 코드가 파트를 직접 순회할 필요가 없었다.

### barge-in 실사용 검증 결과 (완료)

`python scripts/test_live_audio.py`를 사용자가 직접 실행해 확인함. 첫 시도(스피커+마이크, 이어폰 없음)에서 **가만히 듣고만 있었는데도 `interrupted=True`가 떴다** — 원인 규명을 위해 이어폰을 끼고 재시도하자 문제없이 정상 동작(가만히 있을 땐 안 뜨고, 실제로 말을 걸었을 때만 뜸). 즉 첫 시도의 오탐은 barge-in 로직 결함이 아니라 **스피커 소리를 마이크가 되먹임(echo)해서 서버 VAD가 "사용자가 말했다"고 오인식한 것** — 헤드리스 환경에서 헤드폰 없이 스피커+마이크를 물리적으로 가까이 두면 재현되는 전형적인 음향 피드백 문제다.

**실제 로봇에도 적용되는 시사점**: 로봇도 마이크와 스피커가 한 몸체에 붙어 있으므로 이어폰이라는 회피책을 쓸 수 없다. `launcher.py`의 오디오 루프를 만들 때 AEC(음향 에코 캔슬레이션)나 "TTS 재생 중 마이크 입력을 일시적으로 무시" 같은 처리가 필요할 가능성이 높음 — 아직 미해결, `docs/integration-points.md`에 추가 예정.

- Live API/TTS 둘 다 preview 상태라 가격·요청 한도는 여전히 미확인

### 설계 대비 구현 확인

- `play_manual_motion(name: "dance"|"hug"|"greeting"|"wave"|"shy")` — architecture.md §05가 정의한 시그니처와 정확히 일치. `wave`는 v1에 대응 함수가 없어 `greeting`의 별칭으로 처리.

- v1에서 함께 발견했던 `play_both_arms_motion`/`play_right_arm_motion`/`play_left_arm_motion`은 이번엔 **포팅하지 않음** — architecture.md §05의 Layer 1 목록에 없고, 현재는 필요하지 않다고 판단. 단축 관절 하나만 움직이는 재사용 가능한 프리미티브라 Layer 2(`express_gesture`) 구현 시 참고할 소스가 v1에 남아있음.
- 가위바위보/OX퀴즈용 `play_rps_motion`도 미포팅 — architecture.md §09 오픈 이슈로 아직 범위 미결정.

### 자체 리뷰에서 발견해 고친 버그 (커밋 `1e673c6`)

1. **`DANCE_TURN_RPM` 하드코딩 회귀** — 처음엔 `50.0` 고정값으로 넣었는데, v1 원본은 `TURN_RPM * 2`(환경변수로 `TURN_RPM`을 바꾸면 춤 회전속도도 비례해서 바뀜)였다. 그대로 두면 `.env`로 `TURN_RPM`을 조정한 사람은 춤 시퀀스만 옛날 속도로 남는 조용한 회귀였음 — `TURN_RPM * 2`로 수정.
2. **`_perform_shoulder_dance`의 인자 순서 불일치** — motion.py의 다른 모든 함수는 `(port, pkt, lock, ...)` 순서인데 이 함수만 v1 원본 그대로 `(pkt, port, lock, ...)`였다. 실제 호출부는 우연히 다 맞게 호출하고 있어 즉시 터지는 버그는 아니었지만, 같은 파일 안에서 인자 순서가 다르면 다음 수정 때 순서를 헷갈리기 딱 좋은 상태였음 — 통일.
3. **`init.shutdown_all_motors`도 같은 종류의 순서 불일치** — `initialize_robot`과 맞춤.
4. **춤 종료 `finally` 블록의 안전성 결함** — `pygame.mixer.music.stop()`이 블록 맨 앞에서 아무 보호 없이 호출되고 있었다. 믹서가 초기화되기 전에 예외가 나서 춤 루틴이 조기 종료되면, 이 줄에서 다시 예외가 터져 그 아래에 있는 `shared_state['mode'] = 'tracking'` 복구와 팔 원위치 복귀가 전부 스킵될 수 있었음 — 로봇이 `dancing` 모드에 영구히 갇히는 시나리오. `try/except`로 격리해서 음악 정지가 실패해도 안전 복구는 항상 실행되게 수정.
5. **`play_dance()` 재진입 가드 없음** — 춤이 재생 중일 때 다시 호출하면 음악·안무 스레드가 겹쳐 실행될 수 있었음. `threading.Event` 기반 가드(`is_dancing()`)를 추가해 이미 실행 중이면 새 요청을 무시하도록 수정.
6. **테스트 스크립트 종료 시 경합 조건** — 춤이 아직 재생 중인데 사용자가 종료(`q`)하면, `shutdown_all_motors`가 춤 스레드와 동시에 같은 모터에 명령을 보내고 포트를 닫아버릴 수 있었음. 종료 전 `is_dancing()`이 꺼질 때까지 대기하도록 수정.

### 부수적으로 발견한 환경 문제

- **Windows 기본 콘솔(cp949)이 이모지를 인코딩하지 못해 `print()`가 크래시함.** 로봇이 연결되지 않아 `find_dxl_port()`가 못 찾겠다는 경고(⚠️)를 출력하는 순간 바로 재현되는, import 단계에서부터 걸리는 문제였다. `hardware/config.py` 로드 시 stdout/stderr를 UTF-8로 재설정하도록 수정. v1/v2도 실제로 이 문제에 노출되어 있었을 가능성이 있음(터미널 설정에 따라 안 걸렸을 수도 있음).
- **ID 10 모터의 용도가 불명확함.** `config.py` 어디에도 이름이 없는데 v1·v2 `init.py` 모두 위치 1001로 초기화해왔다. 무엇인지 몰라 정체를 확인 못한 채 그대로 보존만 해뒀다 — 실물 로봇에서 확인 필요.
